# Requirements — mm-harness-objective-context-check

## Problem / Purpose

The harness now has:

- canonical objective markdown generated by `context-to-canonical`
- a sidecar JSON intake report with evidence, assumptions, gaps, confidence, and
  optional interview questions

What is still missing is the **gate** between that intake layer and `discover`.
Today a canonical objective can go straight from:

- `context-to-canonical`

to:

- `discover`

without a formal check that the objective is specific enough, evidence-backed
enough, and complete enough to materialize into an execution package.

This objective implements that missing gate as `objective-context-check`.

## Stakeholders / Users

- **Primary:** harness maintainers
- **Secondary:** operators using Claude, Codex, or shell to open new objectives
- **Tertiary:** downstream commands such as `discover --roadmap --existing` and
  future automation over canonical specs

## Scope

### In Scope

- Introduce a new core command/handler for `objective-context-check`
- Validate objective canonical inputs before `discover`
- Support checking by:
  - objective slug
  - explicit canonical file path
- Consume at minimum:
  - canonical objective markdown
  - sidecar intake report JSON
- Produce a structured decision with statuses like:
  - `PASSED`
  - `FAILED`
  - `NEEDS_INPUT`
- Report:
  - missing evidence
  - missing scope boundaries
  - outstanding interview questions
  - confidence/gap summary
- Document the command in the neutral/core path and Claude-compatible path
- Keep the new gate additive to the existing flow

### Out of Scope

- Do not redesign the canonical markdown format wholesale
- Do not rewrite `discover` itself
- Do not build a full interactive questionnaire UI
- Do not add runtime-specific slash-command logic as the primary implementation

## Non-negotiables

- The gate must remain runtime/model agnostic
- `.mm-flow/commands/mm/*.py` remains the source of truth
- `objective-context-check` must distinguish:
  - evidence-backed readiness
  - missing information
  - unresolved interview questions
- A weak or incomplete canonical objective must not be silently treated as ready
- Output must be usable by:
  - another model
  - a human operator
  - downstream automation

## Decisions Already Implied

- The harness target flow becomes:
  - `context-to-canonical`
  - `objective-context-check`
  - `discover`
  - `discover-contract-check`
  - `complete-task`
  - `archive-objective`
- The intake report from the previous objective is now the upstream contract
  surface for this gate
- The first implementation should prefer deterministic checks over subjective
  prose interpretation where possible

## Objective-level Acceptance Criteria

- [ ] `objective-context-check` exists as a core command/handler
- [ ] it can resolve a canonical objective by slug or explicit path
- [ ] it reads the sidecar intake report and evaluates readiness
- [ ] it returns structured statuses (`PASSED`, `FAILED`, `NEEDS_INPUT`)
- [ ] it reports concrete reasons/gaps instead of vague failure text
- [ ] docs show where this gate sits in the harness lifecycle
